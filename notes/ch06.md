# Expert Parallelism
有多個平行feed-forward模組，將token route到其中一個模組處理
token as in 「Token 的隱藏狀態」：「這個字（Token）在神經網路走到目前這一層時，所累積攜帶的『所有特徵與上下文資訊』（在程式裡是一長串的數字向量）」。

「專家並不是一個按主題劃分的模組（例如『數學專家』或『程式碼專家』）。它只是一個可學習的子網路。」

在 AI 的世界裡，他們的分工往往對人類來說是「難以解釋的黑盒子」。他們專精的是「輸入空間的不同區域（Different regions of the input space）」。
例如：  
- 某個專家可能特別會處理「標點符號」或是「轉折語氣」。
- 某個專家可能負責處理某個特定深度的語義特徵。

從數學向量來看，路由器確實是把「特徵相似的 Token」交給了同一個專家，只是這種分類法不一定符合人類的學科分類。

# 🧪 對照我的實驗
> 這章對應 slide 4 第六列「為何 25.2B 只需 active 3.8B」。
> **專家平行（EP）本身需要多卡才能做，但「路由行為」在單卡就能觀察**。
> 完整推導：`scripts/predict_memory_gemma.py`；路由觀測：`scripts/inspect_router_mlx.py`

## 1. Gemma 4 26B-A4B 的 MoE 規格（config.json）

| 項目 | 值 |
|---|---:|
| `num_experts` | **128** |
| `top_k_experts` | **8** |
| `moe_intermediate_size`（每個路由專家） | 704 |
| `intermediate_size`（1 個常駐共享專家） | 2,112 |
| `enable_moe_block` | true（對照組 12B 是 false） |
| router | `Linear(hidden=2816 → 128)`，無 bias |

每個 token 只走 **8/128 = 6.25%** 的路由專家，外加一個**每次都會走的共享專家**。

> **設計取向**：Gemma 4 走的是「**多而窄的路由專家 + 一個常駐共享專家**」路線。
> 128 個寬度只有 704 的專家（相對 hidden=2,816 只有 0.25h），加上一個寬度 2,112 的
> 共享專家負責所有 token 都需要的共通運算。
> 這種設計讓路由更細緻，但也讓負載均衡（E3）更難達成 —— 128 個格子比少數幾個難填平。

## 2. 參數分布

| 項目 | 參數量 | 佔比 |
|---|---:|---:|
| 全部路由專家權重（128 × 30 層） | 22.84B | **佔全模型 90.5%** |
| 每層中 FFN（含共享專家與 router）的佔比 | 779.5M / 814.1M | **95.7%** |
| 每層 FFN 中 active 的部分（8 專家 + 共享 + router） | 65.8M / 779.5M | **8.4%** |
| attention + embedding + norms | 2.39B | 9.5% |
| **層內 active 佔比** | | **12.6%** |

**這張表解釋了三件原本各自獨立的事：**

1. **為什麼 4-bit 能把 47.0 GiB 壓到 12.5 GiB**（見 `ch10.md`）：90.5% 的參數都在
   expert 裡，通用量化一次壓完就是 4.0 倍。
2. **為什麼 LoRA 掛到 expert 上會暴增到 667.4M**（見 `ch01.md` Q2）：
   128 個專家 × 30 層 = **3,840 組矩陣**要掛 adapter，數量本身就是 attention 的 58 倍。
   （對照：12B dense 只有 48 組 FFN，掛滿只膨脹 3.1 倍。）
3. **為什麼活化記憶體跟著 active 3.82B 走**（見 `ch01.md` Q3）：
   每 token 只有 8 個寬度 704 的專家 + 1 個寬度 2,112 的共享專家的中間結果需要保存。
   結果是**參數多 2.1 倍的 26B，活化只有 12B dense 的 40%**（6.11 vs 15.05 GiB @ seq2048）。

**E4 和 E5 是這個專案裡最有研究價值的兩條**，因為它們直接連到提案 slide 10 的
延伸研究方向 B（擴散模型對「在地用語」的可控性）——如果能證明繁中內容
在 MoE 裡有可辨識的路由特徵，那「語言變體作為可控制屬性」就有了機制上的證據。
**這是超出原本 Playbook 驗證範圍的加分項，值得在報告最後單獨提一頁。**

> **128 個專家讓 E4 更有機會成立**：格子越多，路由分布的解析度越高，
> 中英差異越不容易被平均掉。但相對地，樣本數也要夠 ——
> `inspect_router_mlx.py` 預設用 10 對中英 prompt，若 KL 訊號太弱就加 prompt。
> 反過來說，128 個格子配上偏少的 token 數也容易產生假訊號，
> 判讀 KL 時要一併看每層收集到多少 token。

## 5. ⚠️ 兩個實作陷阱

**其一：`Router.__call__` 回傳的是索引，不是 logits。**

mlx-lm 的 `models/gemma4_text.py` 裡：

```python
def __call__(self, x):
    ...
    top_k_indices = mx.argpartition(expert_scores, kth=-top_k, axis=-1)[..., -top_k:]
    top_k_weights = mx.softmax(mx.take_along_axis(expert_scores, top_k_indices, -1), -1)
    return top_k_indices, top_k_weights      # ← 已經是 top-k 索引
```

攔截時直接數 `top_k_indices` 就好。**若再對它做一次 argpartition，得到的分布會完全錯**
（而且不會報錯，只會安靜地給出假數據）。`inspect_router_mlx.py` 已經處理，
並加了「收集到的選擇次數 vs 理論值」的比值檢查來自動抓這種錯。

**其二：不要用名字比對找 router 模組。**

模組樹裡 `layers.N.router`（Router）底下還有 `layers.N.router.proj`（Linear），
dense 的 MLP 也有 `gate_proj`。用子字串比對會一次抓到三種東西。
正確做法是認 **class 名稱 `Router`**，數量應該剛好等於 MoE 層數（30）。

## 6. 專家平行 vs 資料平行（若之後租到 2 卡）

| 策略 | 每卡 expert 權重（4-bit） | 通訊型態 | 每步通訊量 |
|---|---:|---|---:|
| DP（各卡完整複製） | 11.3 GiB | all-reduce 梯度 | **23 MB**（LoRA attn，見 `ch02.md`） |
| EP=2（專家切一半） | **5.65 GiB** | **all-to-all**（token 送去對應專家再送回） | 隨 batch×seq×h 成長，遠大於 LoRA 的梯度量 |

**預測 E6：在 LoRA 情境下 EP 不划算。** 因為 LoRA 的梯度通訊已經小到可忽略（23 MB），
而 EP 的 all-to-all 要搬的是**活化**（每步數百 MB 到數 GB），反而變成新瓶頸。
EP 的價值在全參數訓練或推論服務，不在小規模 LoRA 微調——這也是一個
「課本說 EP 省記憶體，但在我的具體情境下不適用」的誠實結論。

**而 Week 2 多出一個原計畫沒有的證據來源**：12B dense 與 26B MoE 的直接對照。
MoE 用 2.1 倍的總參數、2.1 倍的權重記憶體，換到 32% 的 active 參數
（＝更低的每 token 計算量與記憶體頻寬需求）。**這筆帳划不划算，
由微調後的 TMMLU+ 準確率與實測 tok/s 一起回答** —— 這比純理論推導有力得多。
