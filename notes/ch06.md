# Expert Parallelism
有多個平行feed-forward模組，將token route到其中一個模組處理
token as in 「Token 的隱藏狀態」：「這個字（Token）在神經網路走到目前這一層時，所累積攜帶的『所有特徵與上下文資訊』（在程式裡是一長串的數字向量）」。

「專家並不是一個按主題劃分的模組（例如『數學專家』或『程式碼專家』）。它只是一個可學習的子網路。」

在 AI 的世界裡，他們的分工往往對人類來說是「難以解釋的黑盒子」。他們專精的是「輸入空間的不同區域（Different regions of the input space）」。
例如：  
- 某個專家可能特別會處理「標點符號」或是「轉折語氣」。
- 某個專家可能負責處理某個特定深度的語義特徵。

從數學向量來看，路由器確實是把「特徵相似的 Token」交給了同一個專家，只是這種分類法不一定符合人類的學科分類。

# 🧪 對照我的實驗
> 這章對應 slide 4 第六列「為何 25.2B 只需 active 3.8B」。
> **專家平行（EP）本身需要多卡才能做，但「路由行為」在單卡就能觀察**。
> 完整推導：`scripts/predict_memory_gemma.py`；路由觀測：`scripts/inspect_router_mlx.py`

## 1. Gemma 4 26B-A4B 的 MoE 規格（config.json）

| 項目 | 值 |
|---|---:|
| `num_experts` | **128** |
| `top_k_experts` | **8** |
| `moe_intermediate_size`（每個路由專家） | 704 |
| `intermediate_size`（1 個常駐共享專家） | 2,112 |
| `enable_moe_block` | true（對照組 12B 是 false） |
| router | `Linear(hidden=2816 → 128)`，無 bias |

每個 token 只走 **8/128 = 6.25%** 的路由專家，外加一個**每次都會走的共享專家**。

> **設計取向**：Gemma 4 走的是「**多而窄的路由專家 + 一個常駐共享專家**」路線。
> 128 個寬度只有 704 的專家（相對 hidden=2,816 只有 0.25h），加上一個寬度 2,112 的
> 共享專家負責所有 token 都需要的共通運算。
> 這種設計讓路由更細緻，但也讓負載均衡（E3）更難達成 —— 128 個格子比少數幾個難填平。

## 2. 參數分布

| 項目 | 參數量 | 佔比 |
|---|---:|---:|
| 全部路由專家權重（128 × 30 層） | 22.84B | **佔全模型 90.5%** |
| 每層中 FFN（含共享專家與 router）的佔比 | 779.5M / 814.1M | **95.7%** |
| 每層 FFN 中 active 的部分（8 專家 + 共享 + router） | 65.8M / 779.5M | **8.4%** |
| attention + embedding + norms | 2.39B | 9.5% |
| **層內 active 佔比** | | **12.6%** |

**這張表解釋了三件原本各自獨立的事：**

1. **為什麼 4-bit 能把 47.0 GiB 壓到 13.22 GiB**（見 `ch10.md`）：90.5% 的參數都在
   expert 裡，通用量化一次壓完就是 4.0 倍。
2. **為什麼 LoRA 掛到 expert 上會暴增到 667.4M**（見 `ch01.md` Q2）：
   128 個專家 × 30 層 = **3,840 組矩陣**要掛 adapter，數量本身就是 attention 的 58 倍。
   （對照：E4B dense 只有 42 組 FFN，掛滿只膨脹 3.8 倍。）
3. **為什麼活化記憶體跟著 active 3.82B 走**（見 `ch01.md` Q3）：
   每 token 只有 8 個寬度 704 的專家 + 1 個寬度 2,112 的共享專家的中間結果需要保存。
   結果是**總參數多 3.4 倍的 26B，活化反而比 E4B dense 小 27%**（6.11 vs 8.34 GiB @ seq2048）。

**E4 和 E5 是這個專案裡最有研究價值的兩條**，因為它們直接連到提案 slide 10 的
延伸研究方向 B（擴散模型對「在地用語」的可控性）——如果能證明繁中內容
在 MoE 裡有可辨識的路由特徵，那「語言變體作為可控制屬性」就有了機制上的證據。
**這是超出原本 Playbook 驗證範圍的加分項，值得在報告最後單獨提一頁。**

> **128 個專家讓 E4 更有機會成立**：格子越多，路由分布的解析度越高，
> 中英差異越不容易被平均掉。但相對地，樣本數也要夠 ——
> `inspect_router_mlx.py` 預設用 10 對中英 prompt，若 KL 訊號太弱就加 prompt。
> 反過來說，128 個格子配上偏少的 token 數也容易產生假訊號，
> 判讀 KL 時要一併看每層收集到多少 token。

### 📊 E3 / E4 實測結果（26B-A4B 4-bit，10 對中英 prompt）

| | 繁中 | 英文 |
|---|---:|---:|
| 收集到的專家選擇 | 2,072 次/層（259 tokens × top-8） | 2,016 次/層 |
| 平均變異係數 | **1.89** | 1.82 |
| 取樣噪音下限 | 0.25 | 0.25 |
| 訊號 / 噪音 | **7.6×** | 7.3× |
| 低用量 expert（<平均 1/10） | 1,565 / 3,840 | 1,373 / 3,840 |
| 最熱的 expert | 佔 **10.62%**（平均的 13.6 倍） | 11.66%（14.9 倍） |

**E3 判定：明顯不均衡 ⚠️** —— 而且訊號是噪音的 7.6 倍，不是樣本太少造成的假象。
40% 的 expert 用量不到平均的 1/10，同時有少數 expert 被 13–15 倍地偏好。

這**印證了第 1 節的預測**：「128 個格子比少數幾個難填平」。
對照 slide 4，這條要這樣寫：MoE 宣稱的「每 token 只用 6.25% 的專家」在算術上成立，
但**實際被用到的是哪 6.25%，分布極度不平均** ——
這代表 EP（把專家平均切到多卡）在這個模型上會產生嚴重的負載傾斜，
是 E6「EP 不划算」之外的另一個獨立理由。

| 統計量 | 觀測平均 | H0 下的平均 | 訊噪比 | p<0.01 的層數 |
|---|---:|---:|---:|---:|
| KL（plug-in） | **0.7042** | 0.1063 | **6.6×** | 26 / 30 |
| KL（add-0.5 平滑） | 0.3059 | 0.0430 | **7.1×** | **29 / 30** |
| JSD | 0.0556 | 0.0128 | **4.4×** | **29 / 30** |

**雜訊底線不能用解析式 `(K−1)/(2N) = 0.0306`。**那是 N ≫ K 的漸近展開，
本例 N/K ≈ 16 且四成專家幾乎沒被選到，條件不成立，會低估 3.5 倍。
改用參數化 bootstrap（在 H0 下從合併分布重抽 300 次）直接量，
底線是 0.1063。

**E4 判定：中英路由明顯不同 ✅** —— 這是本專案最有研究價值的一條。
30 層裡有 29 層在 bootstrap 檢定下 p < 0.01（平滑 KL 與 JSD），
**「語言是 MoE 內部可辨識的路由特徵」**有了量化證據，
直接接上提案 slide 10 的延伸方向 B。

而且差異**極度集中**：平均只要 2.9 個專家就涵蓋單層 80% 的 KL，
全模型只有 128 個專家是明確中文傾向的（其中 26 個英文一次都沒用到）。
這讓「只微調中文專家」從構想變成一個有成本估算的提案 ——
每層取 top-3 掛 LoRA r=16 只要 15.2M 參數。細節見 `moe_routing_分析.md`。

> ⚠️ **兩個必須寫進報告的量測方法學重點**（我一開始都寫錯，值得記下來）：
>
> **其一：每個 expert 的期望佔比是 `1/n_experts` 不是 `top_k/n_experts`。**
> 因為 shares 是「除以所有 expert 的次數總和」，全部加起來是 1.0。
> 早期版本誤用 `k/n_e`，讓 cv 被低估 8 倍、「閒置」門檻高到平均值的 80%，
> 結果把明顯不均衡的路由判成「均衡 ✅」—— **結論整個相反**。
>
> **其二：任何分布比較都要先算噪音下限。**
> 每層只有 2,072 次選擇分到 128 個格子，平均每格 16 次；
> 就算路由完全均勻，二項分布的噪音也會造成 cv ≈ 0.25。
> KL 更陰險：plug-in 估計量**有偏**，兩份來自同一分布的樣本也會得到
> 約 (K−1)/(2N) = 0.031 的 KL。**不先算基準，0.70 這個數字什麼都不能說明。**
> 現在腳本每次都會把兩個基準一起印出來。


## 5. ⚠️ 三個 MLX 實作陷阱（都不會報錯，只會安靜給錯答案）

這三個都是實際踩過才發現的，寫進筆記免得重蹈覆轍。

**坑 1：`mlx.nn.Module` 是 `dict` 的子類別 —— 別自己走模組樹。**

只要寫成

```python
if isinstance(v, dict):     ...   # ← 這一支會吃掉每一個 Module
elif isinstance(v, Module): ...
```

第一個分支就會吞掉所有模組，走訪只看得到模組的「內容物」、看不到模組本身。
實際症狀是 dump 出來只有

```
layers.0.router.proj      QuantizedLinear
layers.0.router.scale     array
```

**永遠沒有 `layers.0.router` 這一行**，於是「找到 0 個 router」。
正解：用 mlx 自己的 `named_modules()` / `apply_to_modules()`
（mlx-lm 的 tuner 也是用後者）。

**坑 2：`module.__call__ = wrapped` 攔不到任何東西。**

Python 的 dunder method 在**隱式呼叫**時查的是 type 不是 instance：

```python
mod(x)   →   type(mod).__call__(mod, x)
```

所以指派到 instance 上完全不生效，而且**不會報錯** —— 你只會拿到一份全是 0 的統計，
然後以為「這個模型的路由很均衡」。
正解：patch **class** 的 `__call__`，用 `id(module)` 對回是哪一層，離開時還原。

**坑 3：`Router.__call__` 回傳的是 top-k 索引，不是 logits。**

mlx-lm 的 `models/gemma4_text.py`：

```python
def __call__(self, x):
    ...
    top_k_indices = mx.argpartition(expert_scores, kth=-top_k, axis=-1)[..., -top_k:]
    top_k_weights = mx.softmax(mx.take_along_axis(expert_scores, top_k_indices, -1), -1)
    return top_k_indices, top_k_weights      # ← 已經是 top-k 索引
```

直接數 `top_k_indices` 就好。**再做一次 argpartition 會得到完全錯的分布。**

**共同的教訓**：這三個坑都是「靜默失敗」——
程式跑完、輸出漂亮的表格、數字全錯。所以 `inspect_router_mlx.py` 加了兩道自動檢查：

| 檢查 | 抓什麼 |
|---|---|
| router 模組數量 == MoE 層數（30） | 坑 1（走訪壞掉） |
| 收集到的選擇次數 / (token 數 × top_k × 層數) ≈ 1.0 | 坑 2、坑 3（攔截沒生效或攔錯東西） |

**做量測工具時，一定要有一個「這個數字應該等於多少」的獨立驗算**，
否則靜默失敗會一路帶到報告裡。這句話也適用於 Week 2 的其他量測腳本。

### 實際的模組結構（26B-A4B, mlx-lm 0.31.3）

```
language_model.model.layers.N
├── self_attn.{q,k,v,o}_proj      QuantizedLinear
├── mlp.{gate,down,up}_proj       QuantizedLinear   ← 這是「共享專家」
├── router                        Router            ← 要攔的是這個
│   ├── proj                      QuantizedLinear   （hidden → 128）
│   └── scale / per_expert_scale  array
└── experts.switch_glu            SwitchGLU         ← 128 個路由專家包在一起
    └── {gate,up,down}_proj       array（含 scales/biases）
```

值得注意：**128 個路由專家是打包成一個 `SwitchGLU` 而不是 128 個獨立模組**，
所以「LoRA 掛到 expert 上」在 MLX 裡走的是 `LoRASwitchLinear` 這條路
（見 mlx-lm `tuner/utils.py`），和 dense 的 `LoRALinear` 不同。

## 6. 專家平行 vs 資料平行（若之後租到 2 卡）

| 策略 | 每卡 expert 權重（4-bit） | 通訊型態 | 每步通訊量 |
|---|---:|---|---:|
| DP（各卡完整複製） | 11.3 GiB | all-reduce 梯度 | **23 MB**（LoRA attn，見 `ch02.md`） |
| EP=2（專家切一半） | **5.65 GiB** | **all-to-all**（token 送去對應專家再送回） | 隨 batch×seq×h 成長，遠大於 LoRA 的梯度量 |

**預測 E6：在 LoRA 情境下 EP 不划算。** 因為 LoRA 的梯度通訊已經小到可忽略（23 MB），
而 EP 的 all-to-all 要搬的是**活化**（每步數百 MB 到數 GB），反而變成新瓶頸。
EP 的價值在全參數訓練或推論服務，不在小規模 LoRA 微調——這也是一個
「課本說 EP 省記憶體，但在我的具體情境下不適用」的誠實結論。

**而 Week 2 多出一個原計畫沒有的證據來源**：E4B dense 與 26B MoE 的直接對照，
而且這組配對比原本規劃的 12B 乾淨得多 ——

| | E4B dense | 26B-A4B MoE |
|---|---:|---:|
| 總參數 | 7.46B | 25.23B（**3.4×**） |
| **每 token 實際用到** | 3.97B | 3.82B（**幾乎相同**） |
| 4-bit 權重 | 3.91 GiB | 13.22 GiB（**3.4×**） |

**每 token 的計算量對齊了**，所以「MoE 到底買到什麼」變成一個單變數問題：
多花 9.3 GiB 記憶體養 3.4 倍的參數，換到多少準確率與多少吞吐？
**由微調前後的 TMMLU+ 與實測 tok/s 一起回答** —— 這比純理論推導有力得多。
